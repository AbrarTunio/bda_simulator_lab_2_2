Five ideas you will see happen

A stream is a growing table

Spark runs your DataFrame code again on each micro-batch of new rows and updates the result. Watch the batch bars on the right.

Event time, not arrival time

Windows use event_time, when the thing happened. 2% of events are backdated by 3 to 30 minutes, shown in orange, to imitate devices that buffered offline.

The watermark

"Newest event seen, minus N." Events older than that are dropped, and windows that can no longer change are released from memory.

Output modes

update prints windows as they change. append writes a window only once the watermark has closed it, so files appear late, on purpose.

The checkpoint

A folder holding the Kafka offsets read and the window state. Restart with it and Spark continues exactly where it stopped.

The simulator

Run commands in order. Four terminals are used, just as on the VM: T1 for Kafka admin, T2 for the producer, T3 for the main PySpark shell, and T4 for checking files. Simulated time runs 6 times faster than real time, and "wait" commands run faster still.

What this lab teaches

    

      

        
    
          
  1. A stream is a table that keeps growing. You wrote ordinary DataFrame code; Spark re-ran it on each micro-batch of new Kafka records and updated the result. What streaming adds is time, state and output mode.
    2. 
          
  2. Check the source before you debug the job. An empty streaming output is the normal symptom of almost every mistake, so the console consumer in step 3 is the first thing to run, every time. Kafka hands Spark binary key and value columns, which you cast to string and parse.
    3. 
          
  3. Declare the schema and cast the time. An explicit schema stays the same across restarts. Until event_time is a real timestamp, every window is empty.
    4. 
          
  4. Window on event time and choose a watermark. The watermark decides how long to wait for stragglers. Events older than it are dropped, and windows older than it are released, which is what keeps memory flat for days instead of growing until the job crashes.
    5. 
          
  5. Output mode follows the sink. update is for watching: rows appear as they change. append is for files: each window is written once, after the watermark closes it, so an empty folder for the first minutes is correct.
    6. 
          
  6. The checkpoint is part of the application. It holds the Kafka offsets and the window state. Restarting with it processed the gap minute and wrote no duplicates; a fresh checkpoint started from "latest" and never saw the earlier data.
    7. 
          
  7. Health is two comparisons. Processing rate must keep up with input rate, and state rows must level off once the watermark works. Either one growing without end is a job that will fail.
    8. 
        

        

          
The step 8 question: which count is right?

          
Neither is wrong; they answer different requirements. The narrow 30-second watermark gives final answers quickly and uses little memory, which suits alerting, where a result that arrives 25 minutes late is useless. The wide 60-minute watermark counts the stragglers, which suits billing, audit or compliance reporting, where completeness matters more, and it pays for that with more memory and later final results.

          
So the watermark is a business decision expressed in code: how late can data be and still matter?
